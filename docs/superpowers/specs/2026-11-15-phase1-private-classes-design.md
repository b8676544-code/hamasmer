מערכת אחת, בעברית ומימין לשמאל, שבה המזכירה והמנהלת מנהלות את החוגים הפרטיים של "המסמר" בבני ברק ובדימונה: משפחות, ילדים, פניות, רישומים, קבוצות ומשימות. המערכת יוצרת לבד משימות מעקב ושולחת עליהן מייל.

**שלב 1 מסתיים כש:** המזכירה יכולה לפתוח פנייה, לעקוב אחריה, להפוך אותה לרישום, לשבץ ילד לקבוצה ולנהל את המשימות שלה. כל זה בלי אקסל.

## 6. האוטומציות

**A1 – תאריך לחזרה**
- כשנקבע או משתנה "תאריך לחזרה" בפנייה: נוצרת משימה "לחזור למשפחת X" לאותו תאריך, עם טלפון בבית, פלאפון וקישור לפנייה.
- אם כבר יש משימת A1 פתוחה לפנייה, היא זזה לתאריך החדש.
- אם התאריך נמחק, או שהפנייה עוברת ל"נרשם" או "לא רלוונטי", המשימה הפתוחה מתבטלת.

**A6 – שלושה סימונים יוצרים רישום**
- כשבפנייה מסומנים "חוזה חתום", "אמצעי תשלום הוגדר" ו"צינתוקים": הפנייה עוברת ל"נרשם", ולכל ילד בפנייה נוצר רישום בסטטוס "פעיל" לשנת הלימודים הנוכחית, עם סוג החוג והקבוצה שצוינו בפנייה.
- לילד שלא צוינה לו קבוצה נוצרת משימה "לשבץ את X לקבוצה". המשימה נסגרת לבד כשהרישום מקבל קבוצה.
- האוטומציה פועלת פעם אחת לכל ילד בפנייה. ביטול סימון אחר כך לא מוחק רישום ולא יוצר רישום שני.
- פנייה בלי אף ילד לא יכולה לעבור ל"נרשם". המערכת מבקשת להוסיף ילד.

**A7 – עדיין לא חתמו**
- כשפנייה עוברת ל"נשלח חוזה" נשמר התאריך. אם אחרי 3 ימים "חוזה חתום" עדיין לא מסומן והפנייה עדיין ב"נשלח חוזה", נוצרת משימה "משפחת X עדיין לא חתמה".
- הבדיקה רצה כל בוקר ב-07:00. לכל פנייה נוצרת משימה כזו פעם אחת בלבד.

**A8 – לבדוק אם הכסף הגיע**
- כשנקבע או משתנה "תאריך תשלום צפוי" ברישום: נוצרת משימה "לבדוק אם הכסף הגיע – X" לאותו תאריך.
- אם התאריך משתנה, המשימה הפתוחה זזה. אם התאריך נמחק, או שהרישום עובר ל"עזב" או "סיים", היא מתבטלת.

**כללים לכל המשימות האוטומטיות**

# חלק ב' – פירוט טכני

## 11. ארכיטקטורה

```
דפדפן ──► Next.js (Vercel) ──► Supabase: Postgres + RLS + Auth
                │                    │
                │                    ├─ triggers: A1, A6, A8, audit, נרמול טלפונים
                │                    ├─ pg_cron: A7 (שעתי, פועל כשהשעה בישראל 07), תור המיילים (כל דקה)
                │                    └─ Edge Function `send-emails` ──► Resend
                └─ שליחת קוד כניסה ישירות דרך Resend (בלי תור)
```

- **Next.js** (App Router, TypeScript), Tailwind ו-shadcn/ui במצב RTL, פונט Heebo. הנתונים נקראים ונכתבים דרך Server Components ו-Server Actions עם `@supabase/ssr`, תמיד בהרשאות המשתמשת (anon key + JWT). ולידציה ב-zod, הודעות שגיאה בעברית.
- **service role key** נמצא רק בשרת, ומשמש לשלושה דברים בלבד: הזמנת משתמשת, יצירה ואימות של קוד כניסה, ו-Edge Function של המיילים.
- **לוגיקה עסקית** (אוטומציות, נרמול, חישובים) נמצאת ב-Postgres. המסכים לא משכפלים אותה.
- **סביבות:** פרויקט Supabase `hamasmer-dev` לפיתוח ולבדיקות. פרויקט `hamasmer-prod` נפתח לפני העלייה לאוויר. ב-Vercel: Preview מחובר ל-dev, Production ל-prod. אין Docker מקומי.
- **מיגרציות:** קובצי SQL ב-`supabase/migrations/`, מוחלים עם Supabase CLI (`npx supabase db push`).

## 12. סכמת הנתונים

לכל טבלה עסקית: `id uuid pk default gen_random_uuid()`, `created_at`, `updated_at` (trigger), `archived_at timestamptz null`. שמות ב-snake_case באנגלית. התוויות בעברית נמצאות רק בממשק.

**אינדקסים ואילוצים:**
- אינדקס על `families.mobile_phone`, `home_phone`, `extra_phone` לחיפוש ולזיהוי מתקשר בשלב 5. אין unique על טלפון.
- אינדקס ייחודי חלקי ב-`tasks`: (`source`, `lead_id`) כש-`status = 'open'` ו-`source in ('A1','A7')`. (`source`, `registration_id`) כש-`status = 'open'` ו-`source in ('A6','A8')`.
- ל-A7 נדרשת "פעם אחת לכל פנייה" גם אחרי שהמשימה בוצעה: הבדיקה היא שאין אף משימת A7 לפנייה, בכל סטטוס.

**Views (עם `security_invoker = true`):**
- `children_view`: גיל, `id_masked`, סטטוס וקבוצה נוכחית לפי הרישום הפעיל העדכני. אם אין רישום, לפי הפנייה העדכנית.
- `families_view`: מספר הילדים עם רישום בסטטוס `active`.
- `groups_view`: מספר הרישומים בסטטוס `active`.

**פונקציות עזר:**
- `normalize_il_phone(text)`: מסירה כל מה שאינו ספרה. `972` בהתחלה הופך ל-`0`. מחזירה ספרות בלבד. trigger על `families` ו-`instructors` מנרמל לפני שמירה ובודק: נייד `^05\d{8}$`, קווי `^0[2-9]\d{7}$` או `^07\d{8}$`. `mobile_phone` חייב להיות נייד. `home_phone` ו-`extra_phone` יכולים להיות נייד או קווי.
- `is_valid_il_id(text)`: ריפוד ל-9 ספרות ובדיקת ספרת ביקורת. CHECK על `children.id_number`.
- `next_workday(date)`: שבת עוברת ליום ראשון. בשלב 2 יתווספו ימי החופשה.
- `find_family_by_phone(text)`: מחזירה משפחה לפי כל אחד משלושת הטלפונים. מוכנה למרכזייה של שלב 5 ומשמשת כבר עכשיו לבדיקת הכפילות.

## 13. הרשאות (RLS)

RLS מופעל על כל הטבלאות. שתי פונקציות `security definer` עם `search_path` ריק:
- `app.current_role()`: התפקיד מ-`profiles`, רק אם `is_active`.
- `app.is_verified()`: יש שורה ב-`verified_sessions` עם `session_id = auth.jwt()->>'session_id'`, ששייכת ל-`auth.uid()`, ו-`expires_at > now()`.

**כל policy מתחילה ב-`app.is_verified()`.**

| טבלה | manager | secretary | ruchi |
|---|---|---|---|
| `families`, `children`, `leads`, `lead_children`, `registrations`, `groups`, `instructors` | select / insert / update | select / insert / update | – |
| `class_types`, `branches`, `cities` | select / insert / update | select | – |
| `tasks` | הכול | הכול | select / update רק כש-`assignee_id = auth.uid()`. ב-update מותר לשנות רק `status` |
| `profiles` | select / update | select (שם ותפקיד, לבחירת אחראית) | select של עצמה |
| `app_settings` | select / update | select | – |
| `audit_log` | select | – | – |
| `email_outbox` | select | – | – |
| `login_codes`, `verified_sessions` | – | – | – (service role בלבד) |

- אין policy של `delete` באף טבלה. ארכוב נעשה ב-update של `archived_at`. שחזור (`archived_at` חוזר ל-null) מותר רק ל-manager, ונאכף ב-trigger.
- `instructor`: אין policies, ולכן אין גישה.
- ההגבלה של רוחי לעמודת `status` נאכפת ב-trigger על `tasks`.

## 14. כניסה ואימות דו-שלבי

1. `signInWithPassword`. ה-middleware של Next.js מפנה כל משתמשת שאינה מאומתת למסך `/verify`.
2. Route Handler בשרת (service role): יוצר קוד אקראי בן 6 ספרות, שומר `sha256(code + session_id)` ב-`login_codes` עם תוקף 10 דקות, ושולח את הקוד ישירות דרך Resend. מותרת בקשת קוד חדש פעם ב-60 שניות.
3. אימות: Route Handler משווה hash. הצלחה מוסיפה שורה ל-`verified_sessions` עם `expires_at = now() + 12h` ומוחקת את הקוד. כישלון מעלה את `attempts`. ב-5 כישלונות נקבע `locked_until = now() + 15m`.
4. יציאה מוחקת את השורה מ-`verified_sessions`. job לילי מנקה שורות שפג תוקפן.
5. ב-Supabase Auth: הרשמה עצמית כבויה, אורך סיסמה מינימלי 10, SMTP מותאם (Resend) בשביל מיילי הזמנה ואיפוס סיסמה.
6. הזמנת משתמשת: Server Action של המנהלת קורא ל-`auth.admin.inviteUserByEmail` ויוצר שורה ב-`profiles`. השבתה: `is_active = false` ומחיקת ה-`verified_sessions` שלה.

## 15. האוטומציות – מימוש

- **A1:** trigger `after insert or update of callback_date, status on leads`. upsert של משימת A1 פתוחה לפי האינדקס הייחודי, עם `due_date = next_workday(callback_date)`. ביטול (`status = 'cancelled'`) כש-`callback_date` null או כשהסטטוס הוא `registered` / `not_relevant`.
- **A6:** trigger `before update on leads`. כששלושת הסימונים true והסטטוס אינו `registered`: אם אין שורות ב-`lead_children`, נזרקת שגיאה עם הודעה בעברית. אחרת `status := 'registered'`. trigger `after update` יוצר `registrations` לכל שורה ב-`lead_children` עם `on conflict do nothing`, ומשימת A6 לכל רישום ש-`group_id` שלו null. trigger על `registrations` סוגר את משימת A6 הפתוחה כש-`group_id` מתמלא. מעבר ידני של הסטטוס ל-`registered` בלי שלושת הסימונים נחסם.
- **A7:** trigger קובע `contract_sent_at = now()` במעבר ל-`contract_sent`. פונקציה `app.run_a7()` רצה מ-pg_cron כל שעה, ופועלת רק כשהשעה ב-`Asia/Jerusalem` היא 7: לכל פנייה ב-`contract_sent`, עם `contract_signed = false`, ש-`contract_sent_at <= now() - interval '3 days'` ושאין לה אף משימת A7, נוצרת משימה עם `due_date = next_workday(today)`.
- **A8:** trigger `after insert or update of expected_payment_date, status on registrations`. אותו דפוס של A1.
- **מיילים:** trigger `after insert or update on tasks`. ב-insert של משימה פתוחה נוספת שורה ל-`email_outbox` עם `send_after = greatest(now(), due_date בשעה 07:30 לפי Asia/Jerusalem)`. שינוי `due_date` או `assignee_id` לפני השליחה מעדכן את השורה. `done` / `cancelled` לפני השליחה מסמן `cancelled`.
- **Edge Function `send-emails`:** pg_cron קורא לה כל דקה דרך `pg_net`, עם סוד מ-Vault. שולפת עד 20 שורות `pending` ש-`send_after <= now()` עם `for update skip locked`, ושולחת דרך Resend. הצלחה: `sent`. כישלון: `attempts + 1` ו-`send_after = now() + 5 דקות`. ב-3 כישלונות: `failed`.
- **יומן שינויים:** trigger גנרי `after insert or update` על כל הטבלאות העסקיות. הוא שומר רק את העמודות שהשתנו ואת `auth.uid()`. שינוי שנעשה מאוטומציה נרשם עם המשתמשת שגרמה לו.

## 18. בדיקות

- **Unit (Vitest):** `phone.ts`, `il-id.ts`, סכמות zod.

- **E2E (Playwright):** כניסה עם קוד (הקוד נשלף ב-dev דרך נתיב בדיקה שפועל רק כשמוגדר `E2E_TEST_MODE`); פנייה חדשה ← 3 סימונים ← רישום ← משימת שיבוץ ← שיבוץ ← המשימה נסגרת; רוחי לא מגיעה למסך המשפחות.

- **CI:** GitHub Actions מריץ lint, typecheck ובדיקות unit על כל push. בדיקות DB ו-E2E רצות לפני מיזוג ל-main.

## 19. אבטחה ופרטיות

- RLS על כל הטבלאות, ו-2FA שנאכף ב-RLS.
- service role key ו-Resend key נמצאים רק ב-Vercel env וב-Supabase secrets. לא בקוד ולא ב-git. `.env*` ב-`.gitignore`.
- כותרות אבטחה ב-`next.config`: CSP, `X-Frame-Options: DENY`, `Referrer-Policy`, HSTS.
- `robots: noindex` לכל האתר.
- מיילים בלי ת"ז ובלי פרטי ילד מעבר לשם פרטי.
- אין פרטי אשראי במערכת. `payment_set` הוא סימון בלבד.
- יומן השינויים נשמר 24 חודשים.
- אזור הפרויקט ב-Supabase: `eu-central-1` (פרנקפורט).
